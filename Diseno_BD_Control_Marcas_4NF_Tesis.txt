Resumen ejecutivo
El presente documento propone el diseño de una base de datos SQL para controlar marcas de asistencia de una empresa con aproximadamente 1 600 empleados. El sistema contempla captura desde un agente instalado en cada computador, integración con un portal web para reportes de hasta seis meses y un mecanismo de traslado posterior a tablas históricas. La solución se normaliza hasta Cuarta Forma Normal (4NF), separando hechos independientes como empleados, computadores, marcas, turnos, roles y justificaciones.
Alcance
Se documentan objetivos, supuestos, requisitos, modelo lógico, normalización, diccionario de datos, SQL DDL base, índices, seguridad, auditoría, retención y recomendaciones de implementación. El diseño se plantea para SQL Server por su adopción usual en ambientes Windows corporativos, pero la estructura relacional puede adaptarse a PostgreSQL u otro motor SQL.

1. Planteamiento del problema
La empresa requiere registrar entradas, salidas y eventos relacionados con asistencia mediante un agente local por computador. La información debe estar disponible para consultas operativas recientes, permitir justificaciones ante incidencias y conservar trazabilidad para auditoría y reportes de RR. HH.

2. Objetivos
Diseñar una base de datos SQL robusta para el registro de marcas de asistencia.
Garantizar que el modelo lógico cumpla 1NF, 2NF, 3NF, BCNF y 4NF.
Permitir justificaciones asociadas a una marca específica o a un rango de fechas.
Integrar captura por agente, API y portal web de reportes.
Definir estrategia de retención: datos activos por seis meses y traslado a histórico.

5. Normalización hasta Cuarta Forma Normal (4NF)
La 4NF exige que, además de cumplir BCNF, no existan dependencias multivaluadas no triviales excepto cuando el determinante sea una superclave. En este diseño cada tabla representa un solo tema de negocio y las listas independientes se separan en tablas propias.
Forma normal
Aplicación en el diseño
1NF
Atributos atómicos: cada marca es una fila; no existen columnas Marca1, Marca2 ni listas en un campo.
2NF
Las tablas con clave compuesta, como UsuarioRol, no tienen atributos que dependan solo de una parte de la clave.
3NF
Datos descriptivos como nombre de departamento, puesto o motivo no se repiten en Marca.
BCNF
Las dependencias funcionales relevantes tienen como determinante una clave candidata.
4NF
Relaciones independientes N:M se separan: UsuarioRol, AsignacionTurno, EmpleadoContacto opcional, ComputadorAgente.
Ejemplo de riesgo evitado: si una tabla Empleado contuviera múltiples roles web y múltiples turnos históricos, se produciría una combinación artificial rol × turno. En 4NF se separan UsuarioRol y AsignacionTurno, eliminando redundancia y anomalías de actualización.

8. Reportes web y regla de máximo seis meses
Los reportes deben ejecutarse mediante procedimientos almacenados o servicios backend que validen el rango de fechas. La base de datos puede reforzar esta regla en procedimientos, vistas parametrizadas desde la API y controles del portal. Para consultas históricas se recomienda una opción separada con permisos especiales.
CREATE OR ALTER PROCEDURE asistencia.sp_ReporteMarcasEmpleado     @EmpleadoID BIGINT,     @FechaInicio DATE,     @FechaFin DATE AS BEGIN     SET NOCOUNT ON;      IF DATEDIFF(DAY, @FechaInicio, @FechaFin) > 183         THROW 50001, 'El reporte no puede superar seis meses.', 1;      SELECT m.MarcaID, e.CodigoEmpleado, m.FechaHoraServidor,            tm.Codigo AS TipoMarca, m.EstadoMarca,            j.EstadoJustificacion, j.TextoJustificacion     FROM asistencia.Marca m     JOIN rrhh.Empleado e ON e.EmpleadoID = m.EmpleadoID     JOIN asistencia.TipoMarca tm ON tm.TipoMarcaID = m.TipoMarcaID     LEFT JOIN asistencia.Justificacion j ON j.MarcaID = m.MarcaID     WHERE m.EmpleadoID = @EmpleadoID       AND m.FechaHoraServidor >= @FechaInicio       AND m.FechaHoraServidor < DATEADD(DAY, 1, @FechaFin)     ORDER BY m.FechaHoraServidor DESC; END; GO 
9. Estrategia de históricos

Figura 5. Ciclo de archivo de marcas.
Se recomienda ejecutar un proceso mensual que mueva marcas y justificaciones cerradas con antigüedad mayor a seis meses. El proceso debe usar transacciones, bitácora y validación de conteos antes de eliminar de tablas activas. En SQL Server Enterprise puede evaluarse particionamiento por fecha; en ediciones sin particionamiento, tablas históricas por mes o año pueden ser suficientes.

10. Seguridad, auditoría y rendimiento
El agente debe autenticarse con certificado, token o clave rotada; nunca con credenciales directas de SQL.
La API debe registrar idempotency key para evitar duplicados si el agente reintenta envíos.
El portal debe usar roles; por ejemplo: RRHH_ADMIN, JEFATURA, AUDITOR, EMPLEADO_CONSULTA.
Usar cifrado en tránsito (TLS) y cifrado/mascaramiento para datos sensibles según política institucional.
Planificar backups, pruebas de restauración y monitoreo de crecimiento mensual.
Índices principales: empleado-fecha, fecha global, estado de justificación y claves únicas de catálogos.
11. Estimación de volumen
Con 1 600 empleados y cuatro marcas diarias promedio, el sistema recibiría aproximadamente 6 400 marcas por día hábil. En seis meses laborales se proyectan cerca de 768 000 a 1 150 000 filas, según calendario y cantidad de eventos adicionales. Este volumen es moderado para SQL Server si se aplican índices, mantenimiento y archivo.

Anexo A. Reglas de negocio principales
Una marca pertenece a un único empleado y a un único tipo de marca.
Una justificación pertenece a un empleado y puede referenciar una marca; si la marca no existe, justifica un periodo.
Una marca no debe depender de la hora del computador cliente; la hora oficial es del servidor.
Las consultas operativas del portal no deben exceder seis meses.
Las relaciones multivaluadas independientes se resuelven mediante tablas puente o tablas de vigencia.
